Engineering case study

Static where it should be, dynamic where it matters

omarmassfih.no publishes notes through FastAPI and Turso, compiles them into an Eleventy site, and keeps the interactive chat dynamic. The split gives readers fast, indexable pages without giving up retrieval-backed answers.

01

Build-time note loading

Eleventy asks GET /notes?include=content for the complete published note set. The loader cache-busts the edge-cached endpoint, retries transient failures, normalizes metadata, and sorts the result before exposing it through Eleventy’s data cascade. Note pages, lists, the knowledge graph, feed, and sitemap are then static build artifacts.

Boundary: unavailable or invalid note data fails the build instead of silently deploying a partial knowledge base.

02

FastAPI and Turso publishing

Notes begin as versioned HTML documents with front matter. The seed process parses the tree, initializes the schema, upserts current notes, and removes stale rows. API queries exclude drafts and future publication dates. Changed chunks are embedded separately, so editing one note does not require re-embedding the entire corpus.

Source and tests

  • Parsing, schema, synchronization, and publication filters
  • Asynchronous Turso connection
  • Cached notes endpoints and streaming HTTP boundary
  • Note synchronization command
  • Incremental chunk embedding
  • Notes parsing, filtering, API, caching, and error tests

03

Redeployment and recovery

After notes are seeded and chunks embedded on main, the backend workflow sends a notes_updated repository dispatch. The frontend workflow receives it, rebuilds against FastAPI, verifies the generated site, and deploys the same _site directory to GitHub Pages.

Recovery path: dispatch is skipped when its credential is unavailable. A daily frontend schedule repairs a missed event by rebuilding from the current API state.

04

Streamed hybrid-RAG chat

The browser posts conversation history and parses server-sent events incrementally. The backend embeds the latest question, runs semantic and deterministic BM25 retrieval, fuses both rankings, and expands context with related notes sharing tags. It emits source links before streaming grounded answer deltas through the AI Gateway, ending with [DONE].

Source and tests

  • Grounded prompt, retrieval orchestration, and event stream
  • Chunking, BM25, vector search, fusion, and neighbors
  • AI Gateway client and streamed completion boundary
  • Chat validation, sources, deltas, completion, and failure tests
  • Retrieval, ranking, fusion, and expansion tests

Operating model

Design trade-offs and boundaries

Static delivery, live conversation

Publishing availability is separated from reading availability: generated pages stay online if the backend is down. Chat remains live because streaming and retrieval cannot be precomputed.

Two cache needs

The public notes API uses five-minute edge caching for normal traffic. Builds add a cache-busting query so a content-triggered deployment does not compile stale notes.

Optional capabilities

Embedding and repository dispatch depend on separate credentials. The seed remains useful without either, while chat configuration is validated before a stream begins.

Failure is visible

Build retries absorb transient API failures; exhausted retries stop deployment. The scheduled build is a deliberate backstop for missed cross-repository events.
